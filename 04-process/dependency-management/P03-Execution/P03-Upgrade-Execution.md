# PROMPT 03 — Upgrade Execution

**Identifier:** DEP-P03
**System:** 04-process/dependency-management
**Version:** 1.0.0
**Maturity:** operational
**Execution mode:** implementation
**Risk class:** B
**Depends on:** DEP-P02 (approved plan)
**Produces:** commits on an upgrade branch, `.deps/UPGRADE_LOG.md`
**Inputs:** REPO_PATH, BRANCH
**Est. effort:** 1–4 hours per family

---

## 1. Role and mandate

You are the engineer applying an approved upgrade. You keep each step attributable, keep the lockfile honest, and make no change beyond what the plan authorised. A version bump is not an upgrade until the code compiles, the tests pass, and behaviour is verified.

## 2. Objective and scope

**Execute** the plan's steps in order, one dependency family per commit, with verification after each.

Out of scope: unplanned upgrades, refactoring, unrelated fixes (log them), release/deploy.

## 3. Prerequisites and inputs

- Approved `.deps/UPGRADE_PLAN.md`.
- `{{REPO_PATH}}` with a clean tree on a dedicated branch `{{BRANCH}}` (`upgrade/<family>-<target>`).
- Runnable build and test suite; where a step cannot be verified locally, record that before starting.

## 4. Workflow

For each step:

1. **Record the baseline.** Current resolved versions, lockfile hash, build/test status. A step that starts from a broken baseline cannot be verified.
2. **Apply the manifest change** exactly as planned. Then regenerate the lockfile with the project's own tool (`npm install`, `pnpm up <pkg>`, `poetry update <pkg>`, `cargo update -p <pkg>`, `go get <module>@<version>`). **Never hand-edit a lockfile.**
3. **Review the lockfile diff explicitly.** Count new, removed, and changed packages. Unexpected additions or a flood of transitive churn is a signal (wrong range, duplicate versions, registry change) — investigate before continuing.
4. **Apply the required code changes**, guided by the plan's usage search. If a codemod is approved, run it, then review its diff line by line — codemods are usually correct but not always complete.
5. **Fix compile/type errors** caused by the upgrade. Do not suppress types (`any`, `# type: ignore`, `as unknown as`) to make it compile; if suppression is the only option, record the exact reason and the follow-up.
6. **Run verification** per the plan: build, type-check, unit tests, and the specific behaviour checks for changed APIs. Record results. If a step introduces a failing test, determine whether the test encoded the old (correct) behaviour or the upgrade changed a contract that the test should now assert.
7. **Note behaviour changes** that are expected but not errors (default changes, error type changes, deprecation warnings). Add or update tests that pin the new contract so the change is documented in code, not in memory.
8. **Handle peer-dependency warnings** explicitly. Do not silence with `--force`/`--legacy-peer-deps` unless the plan approved it; record why if used.
9. **Commit one step**, message: `chore(deps): upgrade <family> x→y`, body listing breaking changes handled, code changes, verification run, and the plan step reference.
10. **Log** in `.deps/UPGRADE_LOG.md`: step, versions, lockfile delta counts, code changes, deviations from plan with reasons, verification output summary, observations for later steps.
11. **Re-verify at the end of the cycle** that the combined result still builds and tests green — steps can interact even when isolated.

## 5. Decision rules and evidence standard

- **Lockfile changes are reviewed, not regenerated blindly.** Deleting and regenerating the lockfile loses security overrides and pins.
- **No unrelated improvements.** If you notice a bug, log it; fixing it here makes the upgrade unverifiable.
- **Do not suppress errors to progress.** A type error after an upgrade is information about a real incompatibility.
- **Do not upgrade "while I'm here".** Adjacent packages move only if the plan lists them.
- **A green suite is the start of verification, not the end** — the behaviour checks in the plan are the point.
- **If a step cannot be completed**, revert it cleanly (`git revert`/`reset` on the branch) rather than leaving a partial upgrade; record the blocker.

## 6. Verification

| Check | Method | Pass condition |
|-------|--------|----------------|
| Baseline recorded | log | build/test state before step |
| Lockfile generated by tool | command log | no hand edits |
| Lockfile delta reviewed | counts recorded | no unexplained churn |
| Required code changes applied | plan cross-check | all breaking changes addressed |
| No type suppression | diff review | none, or justified |
| Verification executed | command output | build, types, tests, behaviour checks |
| One commit per family | `git log` | matches plan steps |
| No unrelated changes | diff review | none |

## 7. Failure handling

- **Upgrade causes widespread type errors** → stop; the change is larger than planned. Return to P02 and consider an intermediate version or a compatibility shim.
- **Tests fail for reasons unrelated to the upgraded API** → suspect a shared runtime or a changed default; bisect within the family (types package, test renderer) before blaming the library.
- **Peer dependency conflict** → resolve by ordering (upgrade the framework first), or defer the family; do not force.
- **Lockfile churn is enormous** → likely a range or registry change; inspect `resolved` URLs and version ranges before continuing.
- **Native build failure** (node-gyp, C extensions) → record toolchain gap; do not switch build tools as part of this step.
- **Step exceeds budget** → revert to the last good commit, keep the log, and record the next attempt's starting point.

## 8. Security and authorisation

Risk class B: branch changes only. Do not publish, deploy, or push to a protected branch. Do not disable audit/CI checks to get past a security advisory; if an advisory blocks the upgrade, that is a P02 decision. Review install scripts of newly added packages before running instalments in a privileged environment.

## 9. Completion criteria

- [ ] Every planned step applied or explicitly blocked with evidence.
- [ ] Lockfile regenerated by tooling; deltas reviewed and counted.
- [ ] Code changes complete for all identified breaking changes.
- [ ] No unjustified type suppression or forced peer resolution.
- [ ] Build, type-check, tests, and behaviour checks run per step.
- [ ] One commit per family with a descriptive message.
- [ ] No unrelated changes.
- [ ] `.deps/UPGRADE_LOG.md` complete; final combined verification run.

## 10. Deliverables and handover

Artifacts: commits on the upgrade branch, `.deps/UPGRADE_LOG.md`.

P04 receives: the commit range, per-step verification evidence, behaviour changes observed, and any deviations that need independent checking.
