# PROMPT 05 — Hygiene & Collaboration

**Identifier:** GIT-P05
**System:** 04-process/git-operations
**Version:** 1.0.0
**Maturity:** operational
**Execution mode:** planning
**Risk class:** A
**Depends on:** GIT-P04 (or P01)
**Produces:** `.git-ops/CONVENTIONS.md`
**Inputs:** REPO_PATH, TEAM_SIZE, RELEASE_CADENCE
**Est. effort:** 30–60 min

---

## 1. Role and mandate

You are the engineer turning the team's git practice into a written, checkable convention so it stops being re-litigated and stops being violated by accident. The goal is not a perfect workflow; it is a workflow the team actually follows and a repository that can be trusted.

## 2. Objective and scope

**Produce** a short, enforceable convention covering branch model, commit granularity, merge strategy, review gates, tags, and the repository hazards specific to this project.

Out of scope: mandating a model the team will not adopt, and reorganising the repository (that is a structural change with its own plan).

## 4. Workflow

1. **Observe what the team actually does before proposing anything** in `{{REPO_PATH}}` for a team of `{{TEAM_SIZE}}`: branch naming from `git branch -a`, merge vs squash from `git log --merges`, commit message style from the last 100 subjects, protection rules from the hosting settings, and how often `main` is red. A convention that contradicts current practice must justify the switch.
2. **Choose the smallest model that fits the team and release shape:**

   | Context | Model | Why |
   |---------|-------|-----|
   | Small team, continuous deploy | trunk-based with short-lived branches and feature flags | Fewer conflicts, faster feedback |
   | Regulated / staged releases | release branches plus trunk | Auditability and freeze control |
   | Long release trains, many contributors | Gitflow-style | Only if the cadence genuinely requires it; it is expensive |
   | Single maintainer | trunk with tags | Overhead without benefit otherwise |

3. **Fix the merge policy explicitly**, sized for `{{TEAM_SIZE}}` people releasing at `{{RELEASE_CADENCE}}`: squash, merge commit, or rebase-and-merge — one default, stated, with the reason. Squash loses individual commits (and `bisect` granularity); merge commits preserve structure and clutter history. Pick one and stop arguing.
4. **Define commit granularity**: one logical change per commit, a subject line in the imperative under ~72 characters, a body explaining *why*. Note any enforced format (Conventional Commits) and whether a hook or CI checks it.
5. **Set the review gates**: required approvals, required status checks, up-to-date-before-merge, signed commits where required, and who may bypass (break-glass) and how it is logged.
6. **Decide the tag and release convention**: annotated tags, naming, who creates them, and how a tag maps to a deployable artefact (`04-process/release-engineering/` owns the release itself).
7. **Address repository hazards specific to this project**:
   - lockfiles committed and regenerated by one tool (conflicts are the most common merge pain);
   - large binaries and LFS, or a documented ban;
   - submodules vs monorepo, and how a submodule bump is reviewed;
   - generated code committed or ignored, stated per directory;
   - line endings (`.gitattributes`) so the team does not fight CRLF;
   - secret scanning and what happens when it fires.
8. **Define recovery affordances** so P03/P04 become rare: no plain `--force` (use `--force-with-lease`), protected default branch, a documented "what to do if you lost work" pointer to P04, and a team habit of pushing long-lived work early as a backup.
9. **Make it checkable, not aspirational.** For each rule, name the mechanism that enforces it (hook, CI check, branch protection, review template) or record that it is convention-only and relies on reviewers.
10. **Write `.git-ops/CONVENTIONS.md`:** observed current practice, chosen model with rationale, merge policy, commit rules, review gates, tags, hazards, recovery affordances, and the enforcement mechanism per rule.

## 5. Decision rules and evidence standard

- **Observe before prescribing.** A convention the team already violates daily is worse than none: it trains people to ignore written rules.
- **One merge strategy.** Mixed strategies make history unpredictable and bisect unreliable.
- **Every rule has an enforcement mechanism or an honest "convention only" label.**
- **Prefer fewer, cheaper rules.** Ten enforced rules beat forty aspirational ones.
- **Do not adopt a heavy branching model for a small team**; the cost is paid in merges and delays, and it is not recoverable later without a migration.
- **Record the date and owner** so the convention can be revisited rather than becoming folklore.

## 7. Failure handling

- **Team already has a documented convention** → adopt it as the baseline and only propose deltas; do not rewrite for style.
- **Hosting platform cannot enforce a rule** → mark it convention-only and add a review checklist item; do not claim enforcement.
- **A rule conflicts with a compliance requirement** (signed commits, retention) → the requirement wins; record the trade-off.
- **Migration to a new model is required** (e.g. Gitflow → trunk) → this is a project: sequence it with `04-process/release-engineering/` and communicate before switching, never mid-release.
- **Nobody owns the convention** → assign an owner in the artifact; an unowned rule decays.

## 8. Security and authorisation

Risk class A: analysis and documentation. Do not change branch protection, hooks, or repository settings — record the recommendation and its owner. Do not disable required checks to unblock a merge; that is precisely the control this stage exists to protect.
