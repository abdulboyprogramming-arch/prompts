# PR.md — v1.0.0 run against `_meta/fixtures/pr-scenario/` (2026-10-23)

## TITLE

`feat(onboarding): ONBOARD-01 executes the start procedure instead of quoting it`

## BODY

### What this changes

The prompt a receiver runs when they inherit a codebase now ends in a verdict about whether they can take
over, backed by commands they can re-run. Before this change it produced a description of the codebase: run
as written against the fixture in this PR, it scored **0 of 9** and missed every trap in the fixture,
including a report route that queries a column the schema never creates. Rebuilt, the same prompt on the
same input scores **9 of 9**.

### Why

The gallery line was "join an unfamiliar codebase — where are the traps", and the prompt named none. This
is the handover that now happens weekly: a product built with an AI by someone who cannot describe the
code, handed to a developer who works by hand. `04-process/handover/` assumes a sender who can answer
questions; `02-engineering/project-recovery/` assumes the project is broken; `04-process/documentation/`
assumes someone already understands it. This is the fourth case.

### What this does not prove

- **Scale.** The fixture is six Python files. The prompt's rule for cutting into a large repository —
  follow the money and the personal data first — is argued in §4 and was never exercised.
- **Environment.** The start procedure was really executed (`flask==3.0.3` into a throwaway virtualenv,
  server started, `/health` curled) but no database was available, so every query path 500'd and the
  schema reconciliation was done by reading `schema.sql`, not a live database.
- **Independence.** Author-run. The same person wrote the prompt, the fixture and the grading table, and
  scored the result. There is no second opinion in this PR.
- **Doubt.** The verdict "continue with conditions" is a judgement about product risk, not a finding. C1
  (no authentication on `/reports/<id>`) is clearly blocking; whether C2–C7 are days or weeks is my guess.

### Risk and rollback

Blast radius: Behaviour — the prompt file and nothing else executable. Evidence — eleven fixture files and
two run outputs, inert. Derived — five files that will silently disagree with the tree if the revert is
half-done. Record — changelog, review log, counts prose, all of which will be believed if left stale.

Rollback, in order:

1. `git revert -m 1 <merge-commit>` — restores the skeleton and removes the fixture and evaluation.
2. Regenerate the derived files **after** the revert: `python3 scripts/check_all.py --fix`, then
   `evidence_report.py --write` (the evaluation record is stored in `_meta/evidence.json`; reverting the
   file without the entry leaves the report claiming 39 runs against 38 files).
3. Restore the four prose counts by hand (74 skeletons, 287 operational, 498 files, 13.6%) — the validator
   will fail until they agree with the tree, which is the intended safety net.
4. **A tag or release cut for this change is not retracted by the revert.** If `v2.30.0` exists, it must be
   deleted or annotated as retracted separately, and its notes edited; a revert alone leaves a published
   release describing a prompt that is no longer there.

### Honest limits

Six files is not six hundred. The fixture is small enough to read completely, so the "cut in this order"
rule for a large repository under a tight budget was never needed and is therefore unproven. The 9 of 9 is
author-scored against author-written requirements. Nothing in this PR shows the prompt helps a real
receiver take over a real system; it shows the prompt no longer *permits* the misses the old one permitted.
