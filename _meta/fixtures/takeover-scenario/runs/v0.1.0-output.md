# Onboarding brief — v0.1.0 run

## Big picture
Reportwright-lite is a small Flask service for producing and exporting CSV reports. Its users are
whoever holds an account row; there is no authentication in the repository, so access control is by
deployment. Entry points: the Flask app (`app/main.py`) with two blueprints — reports and export — and a
`/health` route.

## Structure
- `app/main.py` — application factory and runner
- `app/config.py` — environment configuration
- `app/models.py` — data objects (`User`, `Report`)
- `app/routes/__init__.py` — report routes and the query helper
- `app/routes/export.py` — CSV export
- `app/schema.sql` — database schema
- `docs/notes.txt` — the author's notes

The layering is thin: routes contain SQL directly, so there is no repository or service layer.

## Most important code
- `routes/__init__.py::reports_for_user` — the main read path.
- `routes/export.py::export` — the export path.
- `config.py::load_config` — configuration and environment handling; it requires `APP_ENV` and
  `DATABASE_URL`.

## Development workflow
- Install: `pip install -r app/requirements.txt`
- Run: `python -m app.main` from the repository root.
- Tests: none are present. There is no Makefile and no CI configuration.

## Risks and hotspots
- No tests anywhere in the repository.
- SQL is written inline in the routes, so a schema change has no compile-time check.
- `PAYMENTS_KEY` is defined in `config.py` as a placeholder string.
- The Dockerfile exists but has not been verified.
- `docs/notes.txt` mentions a login that no longer exists and an export that "needs a library".

## Start here
1. `app/main.py` -> `app/config.py` -> `app/routes/__init__.py` -> `app/routes/export.py`
2. `app/models.py` and `app/schema.sql` side by side.

## First useful tasks
- Add a test suite around `reports_for_user` and `export`.
- Replace the inline SQL with a small data-access module.
- Verify the Dockerfile builds and runs.
