# PROMPT 02 — Idempotency & Unknown Outcomes

**Identifier:** PAY-P02
**System:** 03-domains/payments
**Version:** 1.0.0
**Maturity:** operational
**Execution mode:** diagnostic
**Risk class:** B
**Depends on:** PAY-P01
**Produces:** `.payments/FLOW_ANALYSIS.md`
**Inputs:** PROVIDER_NAME, API_VERSION
**Est. effort:** 45–90 min

---

## 1. Role and mandate

You are the engineer auditing what happens when things go wrong mid-payment. The dangerous case is not a clean error — it is **not knowing** whether the charge succeeded, and then deciding what to do about it. Every retry, every webhook redelivery, every timeout is a chance to charge twice or to lose a payment entirely.

## 2. Objective and scope

**Prove or disprove** that each money-moving flow is idempotent, that unknown outcomes are handled as a state, and that no failure path can double-charge, silently drop, or leave a payment stuck.

Out of scope: reconciliation against the provider (P03), changing the money model (P01).

## 3. Prerequisites and inputs

- `.payments/MONEY_MODEL.md` (states, transitions, invariants).
- `{{PROVIDER_NAME}}`'s documented retry and idempotency semantics for API version `{{API_VERSION}}`.
- Access to the code paths: checkout, capture, refund, payout, webhook handler, and any job that rescans payments.

## 4. Workflow

1. **Enumerate every money-moving flow**: initial charge, capture (if separated), refund, partial refund, dispute/chargeback ingestion, payout, subscription renewal, and any batch correction job.
2. **For each flow, build the failure table** — this is the core artifact:

   | Failure point | What the caller sees | What the provider did | What our system records | Double-charge risk | Recovery |
   |---------------|----------------------|-----------------------|-------------------------|--------------------|----------|
   | Request sent, response lost | timeout | unknown | pending | high | reconcile by idempotency key |
   | Webhook delayed | success from us | succeeded | pending | low | rescan, not re-charge |
   | Webhook duplicated | success | succeeded | applied twice? | medium | event-id dedupe |
   | Process crash mid-write | error | succeeded | unknown | high | on-start reconciliation |

3. **Check idempotency keys end to end**: is the key generated by us (deterministic, e.g. `order_id + attempt`) and sent to the provider? Is it persisted *before* the request? Is it reused on retry — and never regenerated? A key generated per attempt provides no protection.
4. **Check webhook handling**: signature verification, replay protection (event id store), ordering (a refund can arrive before the capture it refers to), and behaviour when the handler fails halfway. Confirm that redelivery is safe and bounded.
5. **Check the unknown-outcome path explicitly.** When a request times out, the code must not assume failure. It must either query the provider by idempotency key or mark the payment `unknown` and hand it to a reconciler. Record what the code actually does.
6. **Check concurrency**: two workers handling the same order, a double-clicked checkout, two webhook deliveries in parallel, and a refund issued while a capture is settling. Identify the locking or the unique constraint that prevents double application — and whether it exists.
7. **Check retry policies**: are payment calls retried automatically (dangerous without idempotency), with what backoff, and is the retry bounded? Are provider 5xx responses retried, and are 4xx responses treated as terminal?
8. **Check the "stuck" states**: payments that remain `pending` for hours, refunds approved but never sent, authorisations that expired unnoticed. What job rescans them, how often, and what does it do — retry, cancel, or alert a human?
9. **Test the failure paths**, not just read them: simulate a timeout with a fake provider, deliver the same webhook twice, kill the process between the provider call and the database write, and run two captures concurrently against a test key.
10. **Write `.payments/FLOW_ANALYSIS.md`:** the flow list, failure table per flow, idempotency key design, webhook safety, concurrency findings, retry policy, stuck-state recovery, test results, and the specific defects found with severity.

## 5. Decision rules and evidence standard

- **A retry without an idempotency key is a duplicate-charge generator.** Record it as high severity even if it has not happened yet.
- **"Unknown" is never treated as failure.** Treating it as failure causes the double charge; treating it as success hides a lost payment. It is its own state.
- **Idempotency must be enforced server-side**, not only by the UI disabling a button.
- **Webhooks are at-least-once**; the handler must be safe under duplication and reordering. Assume both.
- **Do not test against live payment credentials.** Use the provider's sandbox and a fake that can be told to time out.
- **A finding without a reproduction is a hypothesis.** Simulate it or mark it `unverified`.

## 6. Verification

| Check | Method | Pass condition |
|-------|--------|----------------|
| Every flow has a failure table | inspect | no blank rows |
| Keys persisted before the call | code review | confirmed |
| Keys reused on retry | code review | no regeneration |
| Webhook replay safe | duplicate delivery test | single application |
| Webhook ordering handled | out-of-order test | no invalid state |
| Unknown outcome path exists | code + simulation | query or reconciler |
| Concurrency safe | parallel test | one application |
| Stuck states have a rescanner | code/job inspection | bounded, alerting |
| No live credentials used | environment check | sandbox/fake only |

## 7. Failure handling

- **No idempotency support from the provider** → use a local idempotency table with unique constraints plus a pre-flight query before each retry; record the residual risk.
- **Webhook handler applies changes before verifying the event id** → mark as high severity; duplicate application is a matter of when.
- **Process crash between provider call and DB write** → this is the classic gap; require a write-ahead record (intent) before the call, plus start-up reconciliation.
- **Concurrent workers both capture** → require a database-level guard (unique constraint or `SELECT … FOR UPDATE`); application-level checks are not sufficient under concurrency.
- **Stuck payments exist in production** → do not fix by bulk re-charging; hand to P03 for reconciliation against the provider first.

## 8. Security and authorisation

Risk class B: sandbox credentials and test keys only. Do not run failure simulations against production. Never log full card data, tokens, or provider secrets; redact payloads in artifacts. Any change informed by this analysis follows P03's change-safety rules.

## 9. Completion criteria

- [ ] All money-moving flows enumerated.
- [ ] Failure table per flow, including the unknown-outcome row.
- [ ] Idempotency key design verified end to end.
- [ ] Webhook signature, replay, and ordering handled.
- [ ] Concurrency guards identified and tested.
- [ ] Retry policy reviewed for safe and unsafe retries.
- [ ] Stuck-state rescanner exists and alerts.
- [ ] Failure simulations executed in sandbox; findings severity-rated.

## 10. Deliverables and handover

Artifact: `.payments/FLOW_ANALYSIS.md`.

P03 receives: the unknown-outcome paths, the stuck states, and the defects that require reconciliation rather than code changes.
